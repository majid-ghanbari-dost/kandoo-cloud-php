# ORDER 15 — technical decisions

- P-20: Windows XAMPP PHP/MariaDB with a PowerShell launcher and isolated random demo database, because it avoids downloads and protects existing data; rejected overwriting an existing database/configuration.
- P-20: Bind only the chosen RFC1918 IPv4 address and reject public peers; restrict admin to the owner machine, because HTTP is unencrypted; rejected a public/0.0.0.0 listener and remote admin over cleartext.
- P-21: Reuse the existing escaped, recorded-only invoice receipt and adapt the customer-only styling, because the reference board requires sign-in and the explicit palette is available; rejected guessing new invoice fields or changing the public contract. See Q-P21-DESIGN-BOARD.
- P-21: Permit non-Secure cookies only for the explicit private-LAN demo profile, because browsers reject Secure cookies on HTTP; rejected weakening cookies in production. The trusted LAN is unencrypted and must carry synthetic demo data only.
- P-22: A database-backed demo outbox plus protected local JSON-lines log implements both demo notification and OTP without network calls; rejected changing the Faraz adapter or treating provider acceptance as actual delivery.
- P-23: Preserve mandatory device authentication and mark actual Hub integration blocked when the accessible Hub transport omits credentials; rejected a bypass or representing synthetic golden replay as real Hub proof (Q-P23-HUB-DEVICE-AUTH).
- P-24: Measure 50 simultaneous synthetic unknown-invoice HTTP reads against real local MariaDB using the single PHP built-in worker, because that matches the Windows demo and avoids writes; rejected claiming production capacity or using in-process /health as a DB load test.
- P-20b: Run the full CI suite and installer self-test on both PHP 8.1 and 8.5 with real MariaDB, preserving the existing 8.1 baseline; rejected treating a single PHP version or Linux CI as proof of a Windows execution.
- P-23 C-80b: Record the new Bearer-versus-two-device-header mismatch and retain store-bound authentication until an approved cross-stack wire contract resolves it; rejected bypassing auth or claiming interoperability from independent CI.
- P-27: Resolve Bearer by existing store-scoped SHA-256 digest with ambiguity rejected and explicit Authorization precedence; preserve legacy headers, avoiding a schema migration and preventing downgrade on invalid Bearer. See executive addendum `docs/CONTRACT-ADDENDUM-P27.md`.
- P-23: Halt actual Hub replay on discovering C-80b serializes the device secret into the JSON body as well as the Authorization header; rejected silently altering the real transport or using owner credentials before a C# fix and regression test.
- P-23: Replay pinned C-83 Hub transport over loopback HTTP against isolated real MariaDB with synthetic golden-derived v1.1 data and auth enabled; rejected mocks or independent CI as proof of a real wire call.
- P-25: Handoff records personally inspected CI and unresolved Windows, real-Hub-v1.1 and customer-demo limits; rejected conflating green CI with manager acceptance or full owner-machine proof.
- P-31: Propose an opt-in bearer-authenticated customer invoice list grouped by store, reusing existing OTP/session and D-C controls; rejected returning raw projection rows or changing frozen contract files.
- P-34: Publish bounded security findings and label the existing MariaDB load as nonrepresentative until real host configuration is known; rejected claiming a production capacity or security sign-off from a synthetic single-worker test.
- P-33: Draft fixed notification and single-variable OTP registration templates with an explicit final-domain placeholder and privacy review preserving P-15 evidence; rejected live SMS, unapproved deletion or guessed provider prices.
- P-30: Begin with a non-executable shared-host deployment checklist and explicit restore/self-test gaps; rejected untested backup/restore commands or leaking credentials in a web diagnostic.

- E-72 independent PHP verdict: **INCOMPATIBLE with current consumers**, not a normative rejection of the additive proposal. Direct vector and C# consumer review found quantity/quantity_millis and pre-issue display/provenance differences; Cloud v1.1 rejects cheque and does not project the proposed discount or walk-in fields. A single matching serialization fixture is not runtime compatibility; preserve frozen contracts and seek an explicit cross-lane approved mapping/addendum. The cited C# report incorrectly places image_sha256 and template_library_id at the base_invoice root; both are in provenance. See `docs/reports/E72-PHP-INDEPENDENT-VERDICT-FA.md`.
- PHP-B/P-31+P-34: Give the customer read surface (native list, native detail, `/account/invoices`, `/account/invoices/{store}/{invoice}`, `GET /v1/customer/session`) an independent fixed-window budget — per direct peer (`customer_auth.read_ip_limit_per_minute`, default 120) and per session (`customer_auth.read_session_limit_per_minute`, default 60), keyed by HMAC digests in `customer_read_rate_buckets`, 429 `RATE_LIMITED` + `Retry-After`, 0 disables — because P-34 recorded that the new list endpoint had no independent limiter; rejected reusing the OTP issue/verify budgets (they protect different actions and would couple login and browsing) and rejected disabling the limit by default (an unlimited stolen Bearer is the actual risk).
- PHP-B/P-31: Add `GET /v1/customer/session` as a proposal-only resume check returning `{status:VALID,expires_at}` and no invoice/phone/token data, because the cross-lane C-92 plan requires validating a stored session on the next start-up; rejected making the first list call the only liveness probe and rejected returning the phone number.
- PHP-B/P-30: Prove backup/restore at business level, not only format level — the restored database is exercised through `Kernel` with the pre-backup Bearer, so a restore that silently drops session/announcement state fails CI; rejected stopping at table/row-count equality.
- PHP-B/Load: Seed the customer read benchmark with a synthetic session and DISABLE the read throttle during measurement, because a throttled run measures the limiter instead of the query path; enforcement is proven separately in `CustomerReadLimitDatabaseTest`. Reported numbers remain local evidence only, not E1 capacity.
