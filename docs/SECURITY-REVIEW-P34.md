# بازبینی امنیت و بار P-34 — مرحله‌ای، نه مجوز انتشار

این ارزیابی خواندن کد و آزمون CI است، نه penetration test یا ممیزی شخص ثالث. هیچ دادهٔ واقعی مصرف نشده است.

| محدوده | شواهد و کنترل | یافته / اقدام |
|---|---|---|
| ingest | `IngestService` کلید دستگاه را به فروشگاه محدود می‌کند، hash مقایسه می‌شود، حالت bypass در production مجاز نیست؛ fencing و محدودیت batch وجود دارد. | احراز Bearer پشت FastCGI/پروکسی و محرمانگی header در هاست هدف **NOT-VERIFIED**؛ raw HTTP فقط دموی LAN است. |
| OTP | سهمیهٔ اعلان تأییدشده، قفل configurable، محدودیت device و IP و کلید idempotency در `CustomerAuth`/`CustomerPages` هستند. | ~~IP از peer مستقیم است؛ reverse proxy همه را در یک bucket می‌گذارد~~ — بسته شد: `trusted_proxies` (پیش‌فرض خالی = رفتار قبلی) با حل حق‌ترین hop غیرقابل‌اعتماد از `X-Forwarded-For`؛ هدر بدشکل/بزرگ به peer مستقیم برمی‌گردد (`src/Http/PeerAddress.php`، آزمون `PeerAddressTest`). device token قابل تعویض است؛ عدم وابستگی session bearer به سخت‌افزار در مدل تهدید پذیرفته شده است. |
| admin | به‌طور پیش‌فرض خاموش؛ Basic با password hash، origin/CSRF و cookie ایمن در production. | محدودکنندهٔ اجباری per-direct-peer پیش از بررسی رمز، پیش‌فرض ۱۰ درخواست در دقیقه و قابل تنظیم ۱ تا ۱۰۰۰؛ 429 با Retry-After. تست Memory و MariaDB سبز است. **تصمیم:** این محدودکننده با `trusted_proxies` عوض نمی‌شود — پشت proxy همه در یک bucket می‌مانند و این تنگ‌گیری عامدانه برای مسیر پرخطر admin پذیرفته است؛ مهاجم توزیع‌شده یا تخلیهٔ bucket و لاگ/HTTPS همچنان نیازمند کنترل لایهٔ دسترسی است. |
| public | token با hash ایندکس، مقایسه، پاسخ 404 یکسان، rate limit و no-store؛ HTML escape می‌شود. | نرخ‌سنجی public هم از `trusted_proxies` استفاده می‌کند (بسته شد؛ `PeerAddressTest` تفکیک دو مشتری پشت یک proxy را اثبات می‌کند). محدودکنندهٔ admin عمداً روی peer مستقیم می‌ماند تا در حالت proxy هم fail-safe باشد. استقرار proxy و عدم ثبت URI حاوی token در لاگ وب‌سرور همچنان باید روی میزبان بررسی شود. |
| customer API proposal | Bearer تصادفی و expiry، و فهرست محدود به تلفن session؛ output فیلد هزینه یا profit ندارد. | ~~endpoint فهرست جدید محدودکنندهٔ مستقل درخواست ندارد~~ — بسته شد در PHP-B: بودجهٔ خواندن مستقل per-peer (پیش‌فرض ۱۲۰/دقیقه) و per-session (پیش‌فرض ۶۰/دقیقه) روی فهرست/جزئیات/صفحهٔ مشتری با 429 + `Retry-After` و بدون داده؛ آزمون `CustomerReadLimitDatabaseTest`. رفتار هنگام bearer دزدیده‌شده با نرخ محدود می‌شود ولی حذف نمی‌شود؛ لاگ سرور/پروکسی همچنان باید بررسی شود. |

| customer API read (PHP-B) | بودجهٔ خواندن per-peer و per-session با کلید HMAC (بدون IP یا توکن خام در جدول `customer_read_rate_buckets`)؛ درخواست ردشده شمرده نمی‌شود؛ `GET /v1/customer/session` فقط وضعیت/انقضا برمی‌گرداند. | پشت reverse proxy همهٔ مشتری‌ها یک bucket دارند و باید در لایهٔ proxy جبران شود؛ محدودیت per-device/hardware برای session وجود ندارد (پذیرفته‌شده در مدل تهدید)؛ اثربخشی در برابر نفوذگر توزیع‌شده ارزیابی نشده است. |

## بار

آزمون P-24 در CI برای MariaDB 10.6 و PHP 8.1 اجرا می‌شود: ۱۰۰ GET ساختگی به فاکتور ناموجود، ۵۰ هم‌زمان، loopback، یک worker و rate limit غیرفعال در فایل موقت. نتایج run مشخص در گزارش P-34 آورده می‌شوند. این **معادل پیکربندی واقعی plan E1 نیست**: CPU/RAM، worker و storage میزبان و مسیرهای OTP/admin/ingest ناشناخته‌اند. قبل از ادعای آمادگی میزبان، آزمون دادهٔ ساختگی با پارامترهای ثبت‌شدهٔ میزبان، حفاظت rate limit و سناریوهای کاربردی لازم است. هیچ ادعای ظرفیت تولید یا SLA نشده است.

PHP-B — آزمون بار ساختگی خواندن API مشتری (`tools/dev/load-customer-read.py`، seed ساختگی، loopback، یک worker): ۲۰۰ درخواست (فهرست/جزئیات)، هم‌زمانی ۲۵، صفر خطا، p95 = ۴۴٫۹۴ میلی‌ثانیه در PHP 8.1 با MariaDB 10.6 ([run](https://github.com/majid-ghanbari-dost/kandoo-cloud-php/actions/runs/45966232387))؛ این عدد فقط تأخیر محلی را می‌سنجد؛ عدد آن در artifact اجرا ثبت می‌شود و معادل هاست E1 یا ادعای ظرفیت نیست. بودجهٔ خواندن در این سنجش خاموش است؛ اجرای آن در آزمون واحد اثبات می‌شود.

Backup فقط فایل و digest مورد اعتماد را به DB آزمایشی خالی بازمی‌گرداند. ~~SHA-256 اصالت را تضمین نمی‌کند~~ — بسته شد: با تنظیم `backup_hmac_key` هر آرشیو با HMAC-SHA256 امضا می‌شود و `restore-test` بدون امضای درست پیش از هر DDL رد می‌کند (`BackupAuthenticityDatabaseTest`: امضای غایب/غلط، و امضا بدون کلید). DDL فایل اجرا می‌شود؛ کلید و فایل باید از منبع مورد اعتماد باشند. کنترل مجوز فایل، DDL هم‌زمان، نگهداری، لاگ، HTTPS و بررسی امنیت میزبان و penetration test خارج از شواهد محلی‌اند.
