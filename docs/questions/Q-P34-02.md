# Q-P34-02 — does C-AND-CUST accept the customer throttle vectors?

Status: **OPEN** (asked 2026-11-28 by PHP-B, M-014 standing session). Owner of the answer:
C-AND-CUST. One line back is enough; no meeting.

## Why this is a question and not a task

`docs/BACKLOG.md` PHP-B item 1 reads "P-31 finish **and vectors accepted by the C# side**;
throttling and session tests". The PHP half is delivered:

- `docs/vectors/customer-api-v1-2-proposed.json` — the accepted happy-path vectors, unchanged.
- `docs/vectors/customer-api-throttle-v1-2-proposed.json` — **new**: three independent
  scenarios (per-session budget, per-peer budget, session resume sharing the session budget),
  each with its own limits and a `advance_seconds` step, plus `client_obligations`.
- `tests/Unit/CustomerThrottleVectorTest.php` — replays that file against the real PHP surface
  (green on PHP 8.1 and 8.5 with MariaDB 10.6), so the file cannot drift from the server.

Acceptance is not something PHP-B can perform: it means the client lane replays the same file
against its own double/implementation and says "we match this, or we disagree here".

## The ask (choose one)

1. **Replay and accept.** Add the throttle file to the C-AND-CUST replay set next to the
   P-31 vectors and record the result (run link) in that lane's PR or report.
2. **Replay and disagree.** Reply with the scenario id and the observed difference; PHP-B fixes
   the server or the vector, whichever is wrong, in a follow-up.
3. **Decline for now.** One line saying so, so PHP-B can record the vectors as
   "proposed, client replay waived" instead of leaving the item looking done when it is not.

## What the client lane has to implement either way

The obligations in the file are the practical part and do not depend on acceptance:

- `429 {"status":"RATE_LIMITED"}` = retry later, honour `Retry-After` (60 s), show a retry
  message. It is **not** an authentication failure.
- Never log out and never delete the stored session on 429; only `401 {"status":"UNAUTHENTICATED"}`
  clears the session and returns the customer to the OTP screen.
- The budget is per client address **and** per session: an exhausted Bearer must not block
  another session's screen, and a fast retry loop must stop once `Retry-After` is known.
- A 429 carries no invoice data and `Cache-Control: no-store`; never reuse an older payload.

## Server-side facts the client can rely on (measured, not promised)

- Window: fixed 1-minute bucket; a denied request is not counted; `0` in config disables a limit.
- Behind a reverse proxy the server now keys on the right-most untrusted `X-Forwarded-For` hop
  for the public and customer limiters **only when** `trusted_proxies` lists that proxy; the
  admin limiter deliberately stays on the direct peer.
- Local cost of the two bucket claims: +33…+53 ms p95 per read on a shared CI runner
  (`docs/SECURITY-REVIEW-P34.md`), i.e. real but not a production claim.
