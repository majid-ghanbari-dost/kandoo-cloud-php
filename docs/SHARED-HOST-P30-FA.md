# طرح مرحله‌ای استقرار هاست مشترک E1 — P-30

وضعیت: **ناتمام، برای استقرار واقعی تأیید نشده است**. راهنمای پایهٔ `docs/DEPLOY-GUIDE-FA.md` را بدون تغییر قرارداد بخوانید. هدف PHP 8.1 و MariaDB 10.6 با utf8mb4 است؛ قابلیت‌ها و محدودیت‌های هاست واقعی هنوز بررسی نشده‌اند.

1. پیش از استفاده، مالک HTTPS و ریشهٔ وب را فقط روی `public/` تنظیم کند؛ تنظیمات، کلیدها، log، backup و ابزارهای CLI باید خارج از web root و با مجوز محدود بمانند. کلید یا دادهٔ واقعی در مخزن/گزارش قرار نگیرد.
2. نسخهٔ PHP و افزونه‌های لازم، نسخهٔ MariaDB، مسیر cron، پشتیبانی TLS خروجی و سیاست هاست برای `api.iranpayamak.com` بررسی شود. روش اختیاری IP خروجی با سرویس ثابت ipify و محدودیت حریم خصوصی آن در بخش پایین آمده است؛ روی هاست هدف هنوز آزموده نشده است.
3. DB مجزا با utf8mb4 ساخته و migration طبق راهنمای پایه اجرا شود. بعد از پشتیبان‌گیری، self-test با دادهٔ ساختگی و بدون SMS واقعی انجام شود. `bin/selftest.php --sample` فقط DB آزمایشی `TEST_` را قبول می‌کند؛ ابزار CLI محافظت‌شدهٔ فقط‌خواندنی جداگانه در بخش پایین توضیح داده شده است.
4. cron و heartbeat امن، backup شبانه در محل جدا از DB و web root، سیاست مجوز و retention پشتیبان، و بازیابی روی DB مجزای خالی باید پیاده‌سازی و آزموده شوند. هیچ دستور destructive بازیابی روی DB موجود را بدون فرآیند تأیید و جلوگیری از overwrite اجرا نکنید. آزمون مصنوعی جداگانه در CI انجام شده است؛ انتقال شبانه و مکان فیزیکی جدا و بازیابی عملیاتی هنوز روی میزبان واقعی تأیید نشده‌اند.
5. قبل از هر انتشار، تنظیم proxy، نگهداری لاگ URI/token و محدودسازی admin طبق `docs/SECURITY-REVIEW-P34.md` باید جداگانه بررسی شوند؛ سبز بودن CI معادل تأیید deploy نیست. اگر Cloud پشت reverse proxy می‌رود، فقط آدرس همان proxy را در `trusted_proxies` بگذارید تا سهمیه‌ها per-client شوند؛ فهرست خالی یعنی همهٔ محدودکننده‌ها روی IP مستقیم کار می‌کنند و همهٔ مشتری‌ها یک bucket مشترک دارند. محدودکنندهٔ admin عمداً روی peer مستقیم می‌ماند.

### پیشرفت heartbeat (مرحله‌ای)

Migration `0010_cron_heartbeat.sql` فقط زمان آخرین تکمیل موفق نگهداری را در DB ذخیره می‌کند؛ `bin/cron.php` تنها بعد از موفقیت prune و cleanup آن را ثبت می‌کند. زمان آینده و نبود سابقه سالم تلقی نمی‌شوند و اجرای قدیمی نمی‌تواند زمان را عقب ببرد. مجوز DB و نتیجه باید خصوصی بمانند؛ این به‌تنهایی ابزار پایش/هشدار عملیاتی یا خودآزمایی محافظت‌شده نیست. پیش از فعال‌سازی روی هاست واقعی نسخه پشتیبان معتبر بگیرید، migration را طبق راهنمای پایه اجرا و cron را از حساب محدود میزبان تنظیم کنید. اعلام هشدار و انتقال شبانهٔ پشتیبان هنوز تکمیل نشده‌اند.

### عیب‌یابی محافظت‌شده (CLI؛ هنوز تأیید استقرار نیست)

`bin/host-diagnostics.php` فقط CLI است و بدون کلید مستقل ۳۲ بایتی، به‌شکل ۶۴ رقم hex کوچک، از stdin اجرا نمی‌شود. هش SHA-256 همان رشتهٔ hex در متغیر محیطی `KANDOO_HOST_DIAGNOSTICS_KEY_SHA256` تنظیم شود؛ مقدار واقعی فقط در فایل خصوصی خارج از web root و با مجوز 0600 ذخیره شود و از فایل به stdin هدایت گردد، نه در آرگومان، URL، تاریخچهٔ shell یا لاگ. هش و کلید نباید با رمز یا کلیدهای دیگر مشترک باشند. محیط و حساب CLI را محدود کنید؛ این ابزار endpoint وب ندارد. کلید را پس از افشا فوراً تعویض کنید. خروجی JSON شامل IP و اطلاعات نسخه است؛ فقط برای اپراتور مجاز و بدون ثبت عمومی استفاده شود.

آزمایش PHP، افزونه‌ها، نسخه MariaDB، round-trip فقط خواندنی utf8mb4 با متن ساختگی، تازگی heartbeat و درخواست HEAD از طریق HTTPS بدون کلید به `api.iranpayamak.com` را انجام می‌دهد؛ اتصال TLS نشان‌دهندهٔ تأیید الگو یا تحویل پیامک نیست. IP عمومی با GET ثابت HTTPS به `api.ipify.org` مشخص می‌شود؛ آن سرویس IP عمومی میزبان را می‌بیند، هیچ کلید، شماره یا دادهٔ مشتری به آن فرستاده نمی‌شود. اگر این انتقال یا شبکه میزبان مجاز نیست، ابزار شکست را گزارش می‌کند و IP باید جداگانه با روش مورد تأیید اپراتور بررسی شود. این تست مسیر IP به سرویس echo را نشان می‌دهد و وجود NAT یا مسیر متفاوت تا فراز ممکن است IP دیگری بسازد؛ با provider/هاست تطبیق دهید. سرویس echo در CI فراخوانی نمی‌شود و نتیجهٔ واقعی هاست هنوز NOT-VERIFIED است. آزمون بازیابی مصنوعی CI جایگزین آزمون هاست واقعی نیست.

### پشتیبان منطقی و بازیابی آزمایشی

`php bin/backup.php create <private-separate-directory>` با تنظیم DB منبع فایل JSONL خصوصی و SHA-256 می‌سازد؛ دایرکتوری خارج از web root و جدا از محل DB باشد، محرمانه بماند و انتقال/retention با اپراتور است. برای آزمایش، تنظیم DB را به یک پایگاه **خالی و مجزا** با نام `TEST_RESTORE_` و ۱۲ رقم hex کوچک تغییر دهید و `php bin/backup.php restore-test <trusted-file> <sha256>` اجرا کنید. به DB واقعی یا موجود اشاره نکنید؛ در خطا مقصد آزمایشی ممکن است نیمه‌پر باشد. digest فقط سلامت تصادفی را می‌سنجد نه اصالت. **اصالت (PHP-B / P-34):** اگر در `config.php` مقدار `backup_hmac_key` (۳۲ تا ۲۵۶ بایت، فقط در فایل خصوصی) تنظیم شود، `create` در خروجی JSON کلید `hmac_sha256` را هم می‌دهد و `restore-test` بدون آن امضا، یا با امضای غلط، **پیش از هر DDL** رد می‌کند: `php bin/backup.php restore-test <file> <sha256> <hmac-sha256>`. بدون تنظیم کلید رفتار قبلی (فقط sha256) می‌ماند؛ در حالت عملیاتی کلید را تنظیم کنید. فایل و امضا باید از منبع مورد اعتماد باشند، زیرا DDL اجرا و بررسی foreign key موقتاً غیرفعال می‌شود.

فقط جدول‌های InnoDB و بدون view، trigger، event، routine یا generated column پشتیبانی می‌شوند؛ snapshot تراکنشی است اما DDL هم‌زمان محافظت نمی‌شود. این ابزار بازیابی production نیست. تست CI با دادهٔ ساختگی، migration کامل، CLI و مسیر جدا و مقصد مجزا انجام شد؛ نه Windows/XAMPP واقعی، نه مکان فیزیکی جدا و نه دادهٔ واقعی.
