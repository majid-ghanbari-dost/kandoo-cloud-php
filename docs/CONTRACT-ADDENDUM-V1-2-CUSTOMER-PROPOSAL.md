# Customer API v1.2 — additive proposal, P-31

Status: **proposal**, not cross-team acceptance. Existing frozen files remain unchanged. These routes are opt-in under `customer_auth.enabled`, default off; TLS is required outside the explicit isolated local demo. No legal or tax claims. Existing OTP routes are `/v1/customer/otp/challenges` and `/v1/customer/otp/challenges/{challenge_id}/verify`; JSON POST, `X-Kandoo-Device` is a client-generated 32-byte base64url token (43 characters), protected on the client, present on both calls. Issue also requires `Idempotency-Key`. OTP policy remains D-C: invoice presence, two codes per verified invoice notification, configurable three-attempt lock, device and IP limits. Device tokens are replaceable, not hardware attestation.

On successful verification, the existing response contains `status: OK` and a random bearer session `token`; store it securely on the device, never log it. Expiry and revocation follow the existing customer session policy; no implicit production SMS delivery claim. Use `Authorization: Bearer <token>` with `GET /v1/customer/invoices`. A successful response is `{"stores":[{"store_id":"<uuid>","store_name":"...","invoices":[{"invoice_id":"<uuid>","display_number":1}]}]}`. The server derives the phone from the session, not caller input, and returns only that phone's recorded visible invoices; an empty account returns `{"stores":[]}`. Unauthorized or expired token returns 401 with status `UNAUTHENTICATED`; responses use `Cache-Control: no-store`. No profit, public token, customer phone or purchase price is exposed. No CORS headers are added.

An owned invoice detail may be read at `GET /v1/customer/invoices/{store_id}/{invoice_id}` with the same Bearer. It returns `{ "invoice": ... }` with only recorded store, invoice, lifecycle, issue time, payable, whitelisted line items and recorded optional v1.1 values. A foreign or unknown invoice returns identical 404; missing/invalid session returns 401; the legal-copy gate produces 503. A public token, raw issued payload, purchase price and profit are never returned. The route is opt-in and no existing frozen document is edited.

An authenticated `DELETE /v1/customer/session` revokes the presented session and returns `{ "status": "REVOKED" }` (200); missing, expired or revoked tokens return 401. OTP JSON requests larger than 4096 bytes are rejected.

**Session resume (PHP-B addition, still proposal).** `GET /v1/customer/session` with the same Bearer answers `{"status":"VALID","expires_at":<unix-seconds>}` (200) for a live session, and 401 `UNAUTHENTICATED` for a missing, malformed, expired or revoked token. It returns no invoice, phone or token material, so it is a safe start-up check for a stored session; a client that skips it still learns the same fact from the first list call. Added because the cross-lane plan requires validating a stored session on the next launch.

**Read throttling (PHP-B addition, still proposal).** The list, the detail page and the native lists share an independent fixed-window read budget, separate from the OTP issue/verify budgets: per direct peer address (`customer_auth.read_ip_limit_per_minute`, default 120) and per session (`customer_auth.read_session_limit_per_minute`, default 60). Exceeding either returns 429 with `{"status":"RATE_LIMITED"}` and `Retry-After: 60`; denied requests are not counted and no invoice or ownership information is returned. Both limits may be set to 0 to disable them (local benchmarks do this). Only the direct peer address is used — behind a reverse proxy every client shares one bucket, which must be compensated at the proxy. These are server policy values, not frozen contract fields.

This is a proposal, not a jointly approved Android contract. Shared cross-lane golden vectors, lifecycle and pagination decisions, and any new frozen-contract semantics remain to be reviewed; do not represent this proposal as a finalized shared contract.

Proposed language-neutral sequential replay vectors: `docs/vectors/customer-api-v1-2-proposed.json`. The setup and all data are synthetic; `{{challenge}}`, `{{otp}}` and `{{session}}` are runtime-only values, not fixed secrets. Response objects are required subsets, while arrays and scalar values compare exactly. Each step expects `Cache-Control: no-store`. PHP replays them on MariaDB using a captured fake OTP transport; Android/C# review and independent replay are still pending, and these examples do not change the frozen contract or establish acceptance. Existing separate tests cover other D-C limits; these vectors are not a complete policy specification.
